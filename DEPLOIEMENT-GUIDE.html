Avant de déployer, vérifiez que le serveur Windows 172.25.2.53 dispose des éléments suivants :

A Installer Java 17

Téléchargez Eclipse Temurin 17 (JRE suffit, JDK recommandé) depuis https://adoptium.net et installez-le.

Vérification après installation :

java -version
# Attendu : openjdk version "17.x.x" ...

B Ouvrir le port 8089 dans le pare-feu Windows

Dans PowerShell en tant qu'Administrateur :

New-NetFirewallRule -DisplayName "Monitoring App 8089" `
  -Direction Inbound -Protocol TCP -LocalPort 8089 -Action Allow

2. Installation et configuration PostgreSQL

1 Installer PostgreSQL 16

Téléchargez l'installeur depuis https://www.postgresql.org/download/windows/.

Pendant l'installation, notez bien le mot de passe que vous définissez pour l'utilisateur postgres.

Port par défaut
PostgreSQL s'installe sur le port 5432 par défaut. L'application est configurée pour utiliser ce port.

2 Créer la base de données et l'utilisateur

Ouvrez pgAdmin (installé avec PostgreSQL) ou connectez-vous via la ligne de commande :

# Ouvrir psql en tant qu'admin
psql -U postgres

Puis exécutez ces commandes SQL :

-- Créer l'utilisateur applicatif
CREATE USER monitoring WITH PASSWORD 'monitoring';

-- Créer la base de données
CREATE DATABASE monitoring
  WITH OWNER monitoring
  ENCODING 'UTF8'
  LC_COLLATE 'French_France.1252'
  LC_CTYPE 'French_France.1252'
  TEMPLATE template0;

-- Accorder les droits
GRANT ALL PRIVILEGES ON DATABASE monitoring TO monitoring;

-- Vérifier
\l monitoring
Flyway crée les tables automatiquement
Vous n'avez PAS besoin de créer les tables manuellement. Au premier démarrage, Flyway exécute automatiquement les migrations (V1 à V12) et crée toute la structure ainsi que les données initiales (rôles, utilisateur admin).

3 Ouvrir PostgreSQL aux connexions locales

Par défaut PostgreSQL n'accepte les connexions que depuis localhost. Comme l'application tourne sur le même serveur, aucune modification n'est nécessaire.

Si vous avez besoin de vous connecter depuis une autre machine (ex: pgAdmin depuis votre poste), éditez pg_hba.conf :

# Chemin typique Windows :
# C:\Program Files\PostgreSQL\16\data\pg_hba.conf

# Ajouter cette ligne pour autoriser le réseau interne :
host    all    all    172.25.0.0/16    md5

Puis redémarrer le service : net stop postgresql-x64-16 && net start postgresql-x64-16

3. Déploiement du JAR

1 Créer le dossier de déploiement

# Sur le serveur, créer la structure
mkdir C:\monitoring
mkdir C:\monitoring\logs

2 Copier le JAR

Depuis votre poste de développement, copiez le fichier :

# Depuis votre poste (PowerShell ou Explorateur Windows)
# Chemin source :
D:\Intelligentsia\Monitoring\app\application-monitoring\backend\target\monitoring-backend-1.0.0-SNAPSHOT.jar

# Destination sur le serveur :
C:\monitoring\monitoring-backend.jar
Renommer le JAR
Pour simplifier les commandes, renommez le JAR en monitoring-backend.jar (sans le numéro de version).

3 Premier démarrage (test manuel)

Ouvrez PowerShell en Administrateur sur le serveur et lancez :

cd C:\monitoring

java -jar monitoring-backend.jar `
  --spring.profiles.active=prod `
  --spring.datasource.url=jdbc:postgresql://localhost:5432/monitoring `
  --spring.datasource.username=monitoring `
  --spring.datasource.password=monitoring

Attendez de voir ces lignes dans la console :

INFO  --- [main] o.s.b.w.e.t.TomcatWebServer : Tomcat started on port(s): 8089
INFO  --- [main] o.i.m.MonitoringApplication : Started MonitoringApplication

4 Vérifier l'accès

Depuis n'importe quel navigateur sur le réseau :

http://172.25.2.53:8089

Identifiants par défaut :

ChampValeur
Loginadmin
Mot de passeAdmin123!
Changez le mot de passe admin dès la première connexion
Le compte admin initial doit être sécurisé immédiatement via le module Administration → Utilisateurs.

4. Installation comme service Windows (NSSM)

NSSM (Non-Sucking Service Manager) permet de démarrer l'application automatiquement au boot du serveur et de la relancer en cas de crash.

1 Télécharger et installer NSSM

# Télécharger NSSM depuis https://nssm.cc/download
# Extraire et copier nssm.exe dans C:\Windows\System32\

# Ou via Chocolatey (si installé) :
choco install nssm

2 Créer le service

# En PowerShell Administrateur :
nssm install MonitoringApp

# Renseigner dans l'interface graphique qui s'ouvre :
#   Application Path : C:\Program Files\Eclipse Adoptium\jre-17\bin\java.exe
#   Startup directory : C:\monitoring
#   Arguments        : voir ci-dessous

Arguments du service (copiez en une seule ligne) :

-jar C:\monitoring\monitoring-backend.jar --spring.profiles.active=prod

3 Configurer les logs du service

Dans l'onglet I/O de NSSM :

ChampValeur
StdoutC:\monitoring\logs\app.log
StderrC:\monitoring\logs\app-error.log

4 Gérer le service

# Démarrer
nssm start MonitoringApp
# ou
net start MonitoringApp

# Arrêter
nssm stop MonitoringApp

# Redémarrer
nssm restart MonitoringApp

# Supprimer le service
nssm remove MonitoringApp confirm

# Voir le statut
Get-Service MonitoringApp

5. Vérification et tests

1 Vérifier que l'application répond

# Depuis le serveur (PowerShell) :
Invoke-WebRequest http://localhost:8089/actuator/health

# Réponse attendue :
{"status":"UP"}

2 Vérifier la connexion PostgreSQL

# Dans les logs de démarrage, chercher :
HikariPool-1 - Start completed.
# Ou vérifier via psql :
psql -U monitoring -d monitoring -c "\dt"
# Doit lister toutes les tables créées par Flyway

3 Vérifier la connexion Oracle SVFE

# Dans les logs, chercher :
INFO  SvfeDataSourceConfig - Oracle SVFE datasource initialized
# Si erreur de connexion Oracle, vérifier :
#   - Que le port 1521 est accessible depuis ce serveur
#   - Test ping : ping 172.25.2.53
#   - Test port : Test-NetConnection 172.25.2.53 -Port 1521

4 Tester l'authentification

# Test API login (PowerShell) :
Invoke-RestMethod -Uri http://localhost:8089/api/auth/login `
  -Method POST `
  -ContentType "application/json" `
  -Body '{"login":"admin","password":"Admin123!"}'

# Réponse attendue : { "accessToken": "eyJ...", "refreshToken": "...", ... }

5 Accès depuis un navigateur

Ouvrez http://172.25.2.53:8089 depuis n'importe quel poste du réseau interne. La page de login doit s'afficher.

7. Procédure de mise à jour

Pour déployer une nouvelle version de l'application :

1 Générer le nouveau JAR (poste de développement)

cd D:\Intelligentsia\Monitoring\app\application-monitoring
.\build-prod.ps1
# Le JAR est dans : backend\target\monitoring-backend-1.0.0-SNAPSHOT.jar

2 Arrêter le service

nssm stop MonitoringApp
# ou si démarré manuellement : Ctrl+C dans la fenêtre PowerShell

3 Sauvegarder l'ancien JAR

Rename-Item C:\monitoring\monitoring-backend.jar `
  C:\monitoring\monitoring-backend.jar.bak

4 Copier le nouveau JAR

# Copier depuis votre poste vers le serveur :
monitoring-backend-1.0.0-SNAPSHOT.jar  →  C:\monitoring\monitoring-backend.jar

5 Redémarrer le service

nssm start MonitoringApp
Migrations Flyway automatiques
Si la nouvelle version contient des migrations SQL (nouveaux fichiers V13, V14...), Flyway les appliquera automatiquement au démarrage. Ne supprimez jamais les anciens fichiers de migration.

8. Résolution des problèmes courants

SymptômeCause probableSolution
Page blanche ou erreur 404 à / Le frontend n'est pas dans le JAR Relancer build-prod.ps1 (étape 2 : copie dist/ vers static/)
Erreur "Connection refused" PostgreSQL Service PostgreSQL arrêté net start postgresql-x64-16
Login échoue (mauvais mdp) Migration seed non exécutée Vérifier les logs Flyway au démarrage. Supprimer la DB et redémarrer.
Déconnexion après redémarrage Comportement normal L'app invalide toutes les sessions au redémarrage. Se reconnecter.
Erreur Oracle "ORA-12541" Oracle inaccessible (port 1521) Test-NetConnection 172.25.2.53 -Port 1521. Vérifier le listener Oracle.
Port 8089 inaccessible Pare-feu Windows bloque Voir section 1-B (ouvrir le port avec New-NetFirewallRule)
Erreur "Address already in use" Un autre processus utilise 8089 netstat -ano | findstr 8089 puis taskkill /PID xxx /F
Flyway error: checksum mismatch Fichier de migration modifié Ne jamais modifier un fichier V*.sql existant. Créer un nouveau Vn+1__fix.sql

■ Consulter les logs en temps réel

# Si service NSSM :
Get-Content C:\monitoring\logs\app.log -Wait -Tail 100

# Si démarré manuellement : les logs s'affichent dans la console PowerShell

■ Checklist avant déploiement

  • Java 17+ installé sur le serveur (java -version)
  • PostgreSQL 16 démarré, base "monitoring" et utilisateur "monitoring" créés
  • Port 8089 ouvert dans le pare-feu Windows
  • Accès réseau à Oracle sur 172.25.2.53:1521 vérifié
  • JAR copié dans C:\monitoring\monitoring-backend.jar
  • Premier démarrage testé en mode manuel (console) avant installation en service
  • Page http://172.25.2.53:8089 accessible depuis un autre poste
  • Connexion admin réussie et mot de passe changé
